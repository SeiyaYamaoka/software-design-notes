# Software Design Notes

ソフトウェア設計について広く浅く把握し、必要になった分野を深掘りするための個人用ナレッジベースです。

VitePressを使用して、Markdownで作成した設計ノートをWebサイトとして閲覧できるようにしています。

## 目的

このリポジトリには、以下の内容を整理します。

- ソフトウェアアーキテクチャ
- 設計原則
- デザインパターン
- API設計
- データベース設計
- テスト設計
- セキュリティ設計
- 実務で得た知見

単語や定義を暗記することではなく、次の点を説明できる状態を目指します。

1. 何を解決するための設計か
2. どのような場面で使うか
3. どのような欠点があるか
4. 類似する設計と何が違うか
5. 自分の開発でどう適用できるか

## 方針

### 広く浅く全体像を把握する

最初からすべての分野を深く学ぶのではなく、まずは設計領域全体の地図を作ります。

実務や個人開発で必要になった項目を、その都度深掘りします。

### トレードオフを書く

設計手法を無条件に良いものとして紹介しません。

各ページでは、メリットだけでなく以下の内容も記載します。

- デメリット
- 導入コスト
- 向いていないケース
- 過剰設計になる条件

### AIの出力をそのまま信用しない

記事の初稿作成にはAIを利用しますが、内容は次の情報をもとに確認・修正します。

- 公式ドキュメント
- 技術書
- 信頼できる技術資料
- 実際のコード
- 実務経験

### 実務メモを残す

一般的な説明だけでなく、実際に開発で遭遇した問題や判断も追記します。

例：

- この設計を採用した理由
- 採用しなかった理由
- レビューで指摘された点
- パフォーマンス上の問題
- テストしにくかった構造
- AIが生成したコードの問題点

## 記事の構成

各記事は、原則として以下の構成で作成します。

```text
# 設計名

## 一言でいうと
## 解決したい問題
## 基本構造
## メリット
## デメリット
## 向いているケース
## 向いていないケース
## 実装例
## よくある誤解
## 類似手法との違い
## 自分の実務メモ
## 参考資料
```

すべての項目を無理に埋める必要はありません。

対象となる設計に適した項目だけを使用します。

## 記事追加の手順

1. 対象カテゴリのディレクトリにMarkdownファイルを追加します。
2. 記事テンプレートに沿って初稿を作成します。
3. 公式資料や書籍で内容を確認します。
4. `docs/.vitepress/config.mts`のサイドバーへ追加します。
5. ローカル環境で表示を確認します。
6. 本番ビルドが成功することを確認します。
7. 変更をGitHubへpushします。

```bash
npm run docs:dev
npm run docs:build
```

## AIに記事を作成させる際のルール

- 初学者にも理解できる日本語にする
- 専門用語を使用するときは説明を付ける
- メリットだけでなくデメリットも書く
- 向いていないケースを書く
- 設計を採用すること自体を目的にしない
- 小規模開発と大規模開発の違いを考慮する
- FastAPI、Next.js、PostgreSQLでの例を優先する
- 類似する設計との違いを書く
- 不明な内容を断定しない
- 出典を確認する
- 既存ページとの重複を避ける

## GitHub Pages

`main`ブランチへpushすると、GitHub ActionsによってVitePressサイトが自動的にビルド・公開されます。

VitePressの`base`設定は、GitHubのリポジトリ名に合わせて変更してください。

```ts
export default defineConfig({
  base: "/software-design-notes/",
});
```

公開先の例：

```text
https://ユーザー名.github.io/software-design-notes/
```

このリポジトリの内容は個人学習用です。

AIが生成した文章やコードには誤りが含まれる可能性があります。実際の開発へ適用する際は、プロジェクトの要件、規模、チーム構成、既存設計を踏まえて判断してください。
