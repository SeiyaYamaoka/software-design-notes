# レイヤードアーキテクチャ

## 一言でいうと

アプリケーションを責務ごとの層に分け、層の間の依存関係を整理する設計です。

## 解決したい問題

画面表示、業務ロジック、データアクセスなどの異なる責務が混ざると、変更の影響範囲が広がります。レイヤードアーキテクチャでは、それぞれを別の層に分離します。

## 基本構造

一般的には、次のような層で構成します。

1. プレゼンテーション層
2. アプリケーション層
3. ドメイン層
4. インフラストラクチャ層

実際の層の数や名前は、プロジェクトに合わせて決めます。

## メリット

- 責務の境界を理解しやすい
- 変更箇所を限定しやすい
- チーム内で共通認識を作りやすい

## デメリット

- 小規模な処理では層が過剰になることがある
- 層をまたぐだけのコードが増えやすい
- 依存方向を決めないと密結合になりやすい

## 向いているケース

- 業務ロジックと入出力処理を分離したい
- 機能や開発メンバーが今後増える
- 責務の境界をチームで統一したい

## 向いていないケース

- 処理が非常に小さく、今後も拡張しない
- 層を分けるコストが得られる効果を上回る
