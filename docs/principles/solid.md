# SOLID

## 概要

SOLIDは、オブジェクト指向設計で変更の影響を局所化するための5つの原則をまとめた呼び名です。

原則は採点表ではなく、設計上の問題を見つけるための問いとして使います。すべてのクラスへ機械的に適用したり、原則を守るために抽象化を増やしたりすることが目的ではありません。

## なぜ必要なのか

機能が増えると、変更理由の異なる処理が一つの要素へ集まり、具体的な実装への依存が広がりやすくなります。その結果、小さな変更で無関係な箇所が壊れたり、既存コードを毎回書き換えたりします。

SOLIDは、このような兆候を次の観点から考えるために使います。

- 変更理由が混ざっていないか
- 既存の振る舞いを壊さずに拡張できるか
- 約束した振る舞いを実装が守っているか
- 利用側に不要な依存を強制していないか
- 重要な方針が技術的な詳細に支配されていないか

## 基本的な考え方

### 単一責任の原則（SRP）

一つの要素が、複数の異なる関係者や理由によって変更されないようにします。

「一つのことだけをする」「メソッドを一つだけ持つ」という意味ではありません。同じ目的のために協調して変わる処理は、一つの責務にまとめられます。

### 開放閉鎖の原則（OCP）

頻繁に追加される種類や規則について、既存の安定したコードを毎回変更せずに拡張できる構造を目指します。

既存コードを絶対に変更しないという意味ではありません。変化が実際に繰り返される箇所を見つけ、そこに拡張点を置きます。

### リスコフの置換原則（LSP）

ある型の代わりとして別の型を使ったときに、利用側が期待する振る舞いを壊さないようにします。

メソッド名や引数が同じだけでは不十分です。入力条件を勝手に厳しくする、成功するはずの操作を拒否する、結果の意味を変えるといった実装は、利用側との約束を破ります。

### インターフェース分離の原則（ISP）

利用側に、使わない操作や知る必要のない機能への依存を強制しないようにします。

大きな万能インターフェースを、利用者の役割に応じた小さな接点へ分けます。ただし、一メソッドごとに機械的に分割するのではなく、一緒に使われ、一緒に変わる操作をまとめます。

### 依存性逆転の原則（DIP）

重要な業務上の方針が、データベースや外部サービスなどの具体的な詳細へ直接依存しないようにします。方針と詳細の両方が、利用側に必要な役割を表す抽象へ依存します。

外部からオブジェクトを渡す「依存性注入」は、この関係を組み立てる手段の一つです。注入を使うだけで、依存方向が適切になるわけではありません。

## 判断基準・トレードオフ

SOLIDを検討する前に、実際の変更や問題を確認します。

| 兆候 | 検討する原則 |
| --- | --- |
| 無関係な変更が同じ要素へ集まる | SRP |
| 種類を追加するたびに大きな条件分岐を直す | OCP |
| 実装を差し替えると利用側の前提が崩れる | LSP |
| 利用側が不要な操作にも依存する | ISP |
| 業務ルールが技術的詳細を直接知っている | DIP |

分割や抽象化を増やすと、変更を局所化できる一方で、次のコストが生まれます。

- 要素や名前が増え、処理の流れを追いにくくなる
- 抽象と実装の対応を理解する必要がある
- 起こらなかった変化のために保守コストを払い続ける
- チーム内で境界の意図を共有する必要がある

変更実績がなく、処理も単純な箇所では、直接的な実装の方が理解しやすい場合があります。

## 具体例

通知を送る注文処理を考えます。

```text
[注文を確定する方針] ──> [通知する役割] <── [メール通知]
                                        <── [画面内通知]
```

注文処理がメール送信の設定まで担当していると、注文規則と通知方式という異なる理由で変更されます。通知を別の責務に分ける考え方はSRPです。

注文処理が「通知する役割」へ依存すれば、重要な注文規則を特定の通知方式から切り離せます。これはDIPの適用例です。新しい通知方式を追加するとき、注文処理を変更せずに拡張できればOCPにもつながります。

ただし、通知方式が一つしかなく、変更可能性も低い小さなツールでは、この抽象化は過剰かもしれません。責務が混ざって困ったときに分離できる、読みやすい構造を保つ方が先です。

## よくある失敗

### 原則を一つずつ独立した規則として暗記する

5つの原則は互いに関係しています。責務を分け、利用側に必要な接点を作り、方針を詳細から守るという一連の設計を、異なる角度から見ています。

### クラスを小さくすればSRPを守れると思う

大きさではなく変更理由を見ます。細かく分けた結果、常に複数のクラスを同時変更するなら、かえって一つの責務を分散させている可能性があります。

### すべてを交換可能にする

交換されない実装まで抽象化すると、間接層だけが増えます。変化の頻度と、変更した場合の影響が大きい場所を優先します。

### 継承関係だけでLSPを考える

LSPの中心は、利用側との振る舞い上の約束です。明示的な継承がなくても、同じ役割として交換する複数の実装には同じ観点が必要です。

## まとめ

SOLIDは、変更理由、拡張点、振る舞いの約束、利用側の依存、方針と詳細の関係を見直すための原則です。形式的に適用するのではなく、実際の変更コストを下げられる場所で使います。
