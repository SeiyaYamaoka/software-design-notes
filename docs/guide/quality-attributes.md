# 品質特性と設計判断

## 概要

品質特性とは、ソフトウェアが「どのように良いべきか」を表す性質です。機能が何をするかに対して、品質特性はどの程度速く、安全に、変更しやすく、安定して動くべきかを表します。

代表的な品質特性には、保守性、性能、信頼性、可用性、セキュリティ、使用性、テスト容易性があります。

## なぜ必要なのか

「使いやすく、速く、安全で、変更しやすいシステム」という要求だけでは、設計判断ができません。品質特性同士は、しばしば競合するからです。

たとえば、障害に備えてデータを複数の場所へ保存すると信頼性は高まりますが、構成やデータ同期は複雑になります。厳密な権限確認を増やすと安全性は高まりますが、処理時間や利用者の手間が増える場合があります。

優先する品質を明確にすることで、設計上のコストをどこへ使うか決められます。

## 基本的な考え方

品質特性は、測定可能な状況として表すと判断しやすくなります。

「高速である」ではなく、次のように具体化します。

```text
通常のアクセス量において、
利用者が検索を実行したとき、
95%の要求を2秒以内に返す。
```

この例には、状況、きっかけ、対象、期待する応答、測定基準があります。

設計前に少なくとも次の問いを確認します。

- 誰にとって重要な品質か
- どの状況で必要か
- どの程度なら十分か
- 満たせなかった場合に何が起こるか
- 測定または確認できるか

## 判断基準・トレードオフ

| 品質特性 | 主な問い | 代表的な代償 |
| --- | --- | --- |
| 保守性 | 変更箇所を限定できるか | 抽象化や構成要素が増える |
| 性能 | 必要な時間・処理量を満たすか | キャッシュや並行処理で複雑になる |
| 信頼性 | 誤った結果やデータ損失を防げるか | 検証や冗長化のコストが増える |
| 可用性 | 必要な時間に利用できるか | 複製、監視、復旧手順が必要になる |
| セキュリティ | 不正な利用や情報漏えいを防げるか | 利便性や開発速度と競合する |
| テスト容易性 | 独立して状態や結果を確認できるか | 境界や依存関係の設計が必要になる |

すべての項目で最高を目指すのではなく、「最優先」「必要十分」「今回は重視しない」に分けます。また、品質要求は利用者数や事業上の重要度が変われば見直します。

## 具体例

社内の備品予約と、医療情報の記録では、同じ登録機能でも優先順位が異なります。

備品予約では、短期間の停止を許容して構成を単純にできるかもしれません。一方、医療情報では、正確性、監査可能性、アクセス制御が重要であり、入力履歴や厳密な権限管理にコストをかける理由があります。

「登録システム」という機能名だけでは、適切な設計は決まりません。失敗したときの影響が設計を左右します。

## よくある失敗

### 品質要求を形容詞だけで書く

「高性能」「高可用性」だけでは、達成したか判断できません。具体的な状況と数値、または確認可能な条件へ置き換えます。

### すべてを最優先にする

優先順位がない要求は、実質的に判断を先送りしています。守る品質と、妥協できる品質を関係者と合意します。

### 平均値だけを見る

平均応答時間が短くても、一部の利用者が極端に待たされることがあります。障害時やアクセス集中時など、重要な場面を分けて考えます。

### 実装後に考える

セキュリティや可用性は、完成後に付け足すと構造全体の変更が必要になることがあります。重要な品質は境界を決める前に確認します。

## まとめ

品質特性は、設計の良し悪しを判断する基準です。重要な利用場面を具体化し、優先順位と許容できる妥協を決めることで、必要な設計と過剰な設計を区別できます。
